## Agent Sync (shared with the other developers' agents)

Several people's agents work on this repo at once. The `agent-sync` MCP server is how you avoid editing the same files.

1. **Check in first.** Before any work, call `register_session` with the developer's name, the project (`git remote get-url origin`), the current branch (`git rev-parse --abbrev-ref HEAD`), the HEAD commit (`git rev-parse HEAD`) and a one-line task. If an Agent Sync message at the start of the session gave you a `clientSessionId` and `project`, pass exactly those. Keep the returned `sessionKey` private and pass it to every later call. Read any handoff notes it returns and follow them.
2. **Look up team decisions.** Call `recall` with the project and a few words about the task and follow the decisions and conventions it returns.
3. **Declare intent before editing.** Call `declare_intent` with every file you plan to change and why, before the first edit. If you'll only touch one or two functions or classes in a file, claim those as `path#name` (`src/auth/user.ts#fetchUser`, `src/auth/user.ts#Auth.login`) so others can still edit the rest of it. If it comes back `granted: false`, do not edit those files: tell the user who holds them and why, then pick other work or wait. If it is granted with `warnings`, another developer changed those files recently and their change may not be in your checkout yet: tell the user, pull (`git pull`) or check with them before editing.
4. **Respect the hook.** A hook checks every Edit and Write. If it blocks you with "Agent Sync blocked this edit", do not retry or work around it (no Bash writes, no copying the file): treat it like a `granted: false`.
5. **Stay in sync.** Call `get_updates` between steps. When you change a public interface (function signature, schema, API route, env var), call `remember` with kind `change` so other agents adapt. Save team decisions with kind `decision` or `convention`.
6. **Release when pushed.** Keep your claim until your change is committed and pushed, then call `release` with those paths. Releasing right after the edit lets someone else change the same lines before yours lands, which is a merge conflict. When the task is finished, call `release` with `endSession: true` and a `handoff` saying what was done, what is unfinished, and what to watch out for.
7. **If a call says `SESSION_ENDED`,** your session was closed. If it says to resume, call `register_session` again with `resumeSessionKey` set to your old `sessionKey`, then `declare_intent` for your files again (their claims were freed). Otherwise register a new session.
